Encrypted Password Database (EPDB) security design

How the Encrypted Password Database protects passwords: the key hierarchy, AES-256-CBC field encryption with HMAC-SHA256, multi-user RSA and smart card access, crash-safe saves, access logs, the security measures and their limits.

Release: 2026.107 (database format v2). Audience: security reviewers, administrators and anyone deciding whether to trust EPDB with their passwords. The source code is published, so everything on this page can be checked against it; the design does not depend on keeping it secret.

1. What EPDB protects, and from whom

An EPDB database is a pair of files, name.ehd (the records) and name.ehx (the index). Every record field is encrypted. The goals are:

  • Confidentiality at rest: someone who copies the files, a backup or a lost laptop's disk cannot read the passwords without a credential that opens the database.
  • Integrity: a change made to the files outside EPDB, such as an edited, removed, moved or added record, is detected when the database is opened.
  • Separate credentials per person: several administrators open the same database with their own RSA key or smart card, and one can be removed without sharing a new secret with the rest.
  • No secrets in scripts: scripts and services read one value at run time, with the credential in a file only their account can read, never on the command line.
  • No lost saves: a crash, kill or power loss never leaves a half-written database.

EPDB does not protect against an attacker who controls the computer while the database is open (malware that reads the program's memory, the screen or the keyboard), against a weak password chosen for a password-only database, or against someone who already has a valid credential.

2. The key hierarchy

Each database has one random 256-bit master key. Every credential is just a way to recover that master key, and the master key is never stored in the clear.

  • Password or key file: PBKDF2-HMAC-SHA256 with 600,000 iterations and a random 32-byte salt per database turns it into the master key. The iteration count slows down offline guessing; it does not make a short or common password safe.
  • RSA keys and smart cards: each such user has a key block in the database that holds the master key encrypted to that user's RSA public key with OAEP padding (SHA-256). An RSA user decrypts it with their private key file; a smart card user's card decrypts it with the private key that never leaves the card (PKCS#11). Adding a user needs only their public key or certificate. EC card keys are refused, because they cannot decrypt a wrapped key.
  • Derived keys: KBKDF-HMAC-SHA256 derives four independent keys from the master key: field encryption, field MAC, key check and database MAC, each with its own label, so no key is used for two purposes.
  • Key check: a value derived from the master key tells EPDB whether a credential is right before any record is decrypted, so a wrong credential fails cleanly and is counted (section 6).

3. Field encryption and integrity

  • Every field of every record (title, user name, password, notes and the other columns) is encrypted separately with AES-256 in CBC mode and a new random IV each time it is written.
  • Each encrypted field carries an HMAC-SHA256 tag over the IV and ciphertext, checked before decryption, so a changed or swapped ciphertext is rejected instead of decrypted.
  • Whole-database MAC: a second HMAC-SHA256, kept in the database header, covers the header, the settings, the user key blocks and every record, bound to each record's place in the file and each field's number. Opening a database checks it and checks that the index lists exactly the records in the data file, so records cannot be removed, moved, added or hidden from the index without detection.
  • If a check fails, EPDB refuses the database and says so. --reseal-db accepts the current contents only when an administrator knows why the file changed.
  • Cryptography comes from OpenSSL 3.5 (an LTS release). Random values come from the OpenSSL random generator.

4. Crash-safe saves and the writer lock

  • Every change (a record, an import or merge, settings, users, the in-file access log) is written to a write-ahead journal first, then to the database, so a crash, kill or power loss leaves the state before or after the save, never a mix. Command line changes are made on a copy that replaces the database in steps that are finished at the next open.
  • Only one program at a time can open a database for writing; others are refused with "open in another program" (exit code 4). Reading is not blocked.
  • A journal is replayed only when the user owns it and no other user could have written it or its folder, so another account cannot plant changes through a journal.

5. Users, revocation and automation

  • Remove a user: deletes that user's key block. A user who already recovered the master key could still use it, so the follow-up is --rekey: a new master key, every field encrypted again, every kept user rewrapped with their public key, and a new salt even when the password is kept.
  • Password-less databases: a rekey can drop the password, so that only the RSA and smart card users can open the database.
  • Scripts and services: epdb_auth_tool reads passwords, passphrases and PINs from files only the user can read or from file descriptors, never from the command line, and refuses to prompt in --non-interactive mode. --get-field writes only the one value requested, and it is never logged.

6. Other security measures

  • Smart card PIN safeguards: the PIN is sent at most once per run and never retried. A card that reports low or final PIN tries, or a locked PIN, is not used without asking, so EPDB never locks a CAC.
  • Tamper-evident access log: optional, records each open and change (time, user, method, action, result; never a password, PIN or record value). Entries are chained with HMAC-SHA256 keyed from the master key, so changed, removed, reordered or inserted entries are found. An optional encrypted copy of the last 160 entries is kept in the database file.
  • Self-destruct: optional. After a set number of failed opens through EPDB's programs, the key blocks, the salt, the settings and every record are overwritten with random data.
  • Files and memory: on Linux the program's folders are mode 700 and its private files mode 600. The GUI locks itself after a set idle time and clears copied values from the clipboard after a set number of seconds; printing shows passwords only when that is ticked.
  • Older databases: format v1 databases (2025 and earlier) still open, with a warning, and upgrade to v2 with a backup copy kept.

7. Limits, stated plainly

  • A database that opens with a password is only as strong as that password: anyone with a copy of the files can guess offline at the speed PBKDF2 allows. Use long random passwords, or RSA keys and smart cards.
  • Self-destruct only counts guesses made through EPDB. It does not stop an offline attack on a copy, and the counter cannot be protected against someone who edits the file.
  • Removing whole entries from the end of the access log cannot be detected.
  • While a database is open, its keys are in the program's memory.
  • Backups are encrypted the same way as the database, and they keep working with the credentials that opened them at the time, including those of users removed later.

8. FIPS 140-3

EPDB uses only algorithms approved for FIPS 140-3 (AES-256, SHA-256, HMAC, PBKDF2, KBKDF, RSA-OAEP), and the Windows builds include the OpenSSL 3.5 FIPS provider. EPDB itself is not a FIPS-validated module and does not run in a FIPS-only mode, so it should not be described as FIPS compliant or FIPS validated. Sites that require FIPS-validated cryptography should check their policy with their security office. The companion file encryption tool, fcrypt, has a FIPS mode that uses the OpenSSL FIPS provider.

9. Quantum computing

A large quantum computer, if one is built, would change which parts of today's cryptography stay safe. Where EPDB stands in release 2026.107:

  • Quantum-resistant: AES-256 field encryption (the best known quantum attack roughly halves its strength, which leaves about 128 bits), HMAC-SHA256, PBKDF2 and the key derivation. A database opened only with a password or a key file uses no public-key cryptography.
  • Quantum-resistant users: an RSA key or smart card user can also be given an ML-KEM-1024 key (NIST FIPS 203, from OpenSSL 3.5). The user's key block then wraps the master key with AES-256 Key Wrap under a key derived (KBKDF-HMAC-SHA384) from both an ML-KEM-1024 shared secret and 32 random bytes that only the user's RSA key or card can decrypt, so an attacker must break both RSA and ML-KEM-1024. Opening needs the RSA key or card and the ML-KEM key file (--pq-key); the ML-KEM key files are made with --generate-pq-key and are the same files fcrypt uses.
  • Plain RSA and smart card users are not quantum-resistant: a quantum computer that can break RSA could recover the master key from such a block, also from a copy taken today ("harvest now, decrypt later"). Move them to quantum-resistant users with --rekey, and use --require-pq so that no RSA-only user is added or kept.
  • Smart cards: today's CAC and PIV cards hold RSA and elliptic-curve keys only, so the card half of a quantum-resistant block is RSA; the ML-KEM half is a key file the user keeps.
  • This follows the NSA CNSA 2.0 and NIST guidance to move from RSA to ML-KEM with AES-256.
